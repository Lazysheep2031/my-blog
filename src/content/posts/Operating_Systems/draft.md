### 性能表：比较数量级，而非背诵设备参数

课件第 50 页通过寄存器、缓存、主存和磁盘的对比，说明不同层次在容量、技术、访问时间、带宽、管理者和后备存储上的差异。

| 层次 | 课件给出的访问时间 | 课件模型中的主要管理者 | 下一级后备 |
| --- | --- | --- | --- |
| 寄存器 | 0.25–0.5 ns | 编译器进行寄存器分配 | 缓存 |
| 缓存 | 0.5–25 ns | 硬件 | 主存 |
| 主存 | 80–250 ns | 操作系统 | 磁盘 |
| 磁盘 | 5,000,000 ns | 操作系统 | 光盘或磁带 |

**这些数值是课件的示例参数，不能作为当前硬件规格。** 表中“管理者”也是按主要职责划分：层次间的数据移动可以由程序显式安排，也可以由硬件或系统隐式完成。

<details>
<summary>按课件数据计算：一次磁盘访问相当于多少次主存访问时间？</summary>

这里只比较表中的访问时间，忽略传输数据量、并行性与缓存等因素。

$$
5{,}000{,}000\ \text{ns}=5\ \text{ms}.
$$

与 80–250 ns 的主存访问时间比较：

$$
\frac{5{,}000{,}000}{250}=20{,}000,
\qquad
\frac{5{,}000{,}000}{80}=62{,}500.
$$

因此，按这张表，一次磁盘访问时间约为一次主存访问的 **2 万至 6.25 万倍**。这是由课件参数计算的比值，不能直接当成整个程序的加速比。

### 同一数据在多层中的副本

课件第 51 页跟踪整数 A 从磁盘到寄存器的迁移：

```text
磁盘中的 A → 主存中的 A → 缓存中的 A → 寄存器中的 A
```

> **[截图占位 08｜整数 A 的迁移]**
> 截取 `ch1.pdf` 第 **51 页**，标题 **Migration of Integer A from Disk to Register**，中部四个存储位置与标有 A 的连接箭头。无需截取整页文字。

假设 CPU 修改了寄存器中的 A，那么其他层的旧副本可能还没有同时改变。此时问题从“数据在哪里”扩展为：**后续访问应该得到哪个版本，多个副本怎样保持一致？**

| 环境 | 需要关注的问题 |
| --- | --- |
| 多任务 | 不同进程交替访问有关数据时，不能错误地使用过期值 |
| 多处理器 | 多个 CPU 可能分别缓存同一数据，需要硬件支持缓存一致性 |
| 分布式系统 | 不同机器上还可能有多个副本，更新传播与协调更复杂 |

**缓存一致性（Cache Coherency）** 用来协调多个缓存中的共享数据副本。这里先掌握问题来源；具体协议与内存访问规则不在本章展开。

<details>
<summary>教材思考题 1.10：缓存解决什么问题，又带来什么问题？为什么不把全部慢存储换成缓存？</summary>

根据本节机制整理：

**收益**：让重复访问尽量命中快存储，缩短访问时间；同时减少对较慢层的访问需求，缓解速度差距。

**代价**：缓存空间有限，需要管理内容与替换；一份数据出现多个副本后，需要处理更新和一致性问题。

**不能简单无限扩大**：高速介质的单位成本、可实现容量、能耗及断电保持能力等约束，与慢速大容量存储不同。分层正是利用各类介质的不同优势。

这也说明，缓存价值需要结合工作负载和成本评价；容量越大，并不自动表示整体系统设计越合理。

*题目：教材 pp. 53–54；依据：§1.2.2、§1.5.5。*

</details>

## 多道程序、分时与操作系统运行

> 本节对应后续课件第 52–55 页，结合教材 §1.4 整理。

### 多道程序：让等待期间仍有工作可做

**多道程序设计（Multiprogramming）** 把多个作业的代码和数据组织起来，使系统能够在一个作业等待时改执行另一个作业，从而提高 CPU 利用率。

```text
作业 A 使用 CPU → A 等待 I/O
                       ↓
                  改执行作业 B
                       ↓
              B 需要等待时，再选择其他可运行作业
```

系统中只有部分作业驻留主存，操作系统从中选择可执行的工作。**只要仍有可运行工作，CPU 就有机会继续忙碌**；若所有作业都在等待，CPU 仍可能空闲。

教材用律师同时处理多个案件作类比：一个案件等待开庭或材料时，可以处理另一个案件。提高利用率的关键是利用等待空隙。

课件第 53 页画出“操作系统 + 作业 1–4”同时驻留主存的布局。它说明多个作业共存的概念，不要求实际内存总按图中几个连续大块组织。

### 分时：让多个任务都能及时得到响应

**分时（Time Sharing）** 是多道程序的逻辑扩展。CPU 在任务之间频繁切换，使用户能够在程序运行期间与之交互，因此课件也将其与多任务联系起来。

| 机制 | 主要目标 | 要解决的问题 |
| --- | --- | --- |
| 多道程序 | 提高 CPU 利用率 | 一个任务等待时，有其他工作可执行 |
| 分时 | 提供及时的交互响应 | 不能让一个任务长时间占着 CPU，使其他交互请求一直等候 |

课件提出“响应时间小于 1 秒”作为交互目标的直观说明。理解重点是**合理、及时的响应**，不应把这一数字当作所有系统统一规定的阈值。

**并发**表示多个任务在一段时间内交替或同时推进；**并行**强调它们在同一时刻由不同执行单元实际执行。单核可以通过切换实现并发，多核还可以提供并行执行机会。

### 由多任务引出的管理问题

| 概念 | 要解决的问题 |
| --- | --- |
| 作业选择／调度 | 系统中的哪些作业获得进入执行环境的机会 |
| CPU 调度（CPU Scheduling） | 多个工作都已准备好时，下一步让谁使用 CPU |
| 内存管理 | 多个程序怎样同时驻留，各自占用哪些区域 |
| 交换（Swapping） | 内存不足等情况下，将进程移出主存，之后再移回继续运行 |
| 虚拟内存（Virtual Memory） | 允许进程在没有全部装入物理内存时执行，分离程序看到的地址空间与实际物理存储 |

**“当前要执行的指令和访问的数据需要可供 CPU 使用”与“整个程序必须同时驻留物理内存”是不同要求。** 虚拟内存放宽的是后一个要求，具体如何按需取得缺少的部分将在后续章节讨论。

*来源：课件第 52–53 页；教材 §1.4.1，pp. 23–24；交换补充见 §3.2，pp. 113–114。*

### 用户态与内核态

多个程序共享计算机时，必须防止某个程序执行危险指令、破坏其他程序或修改操作系统。因此需要硬件支持不同权限的执行模式。

**双模式运行（Dual-Mode Operation）** 区分**用户态（User Mode）**与**内核态（Kernel Mode）**。课件用一个由硬件维护的模式位说明：0 表示内核态，1 表示用户态。

| 执行模式 | 权限与用途 |
| --- | --- |
| 用户态 | 运行一般用户代码，不能随意执行受保护的操作 |
| 内核态 | 运行需要较高权限的系统代码，可执行特权指令 |

**特权指令（Privileged Instruction）** 只能在相应特权模式下执行。用户程序试图越权执行时，硬件需要阻止该操作，并把问题交给操作系统处理。

```text
用户代码
   ↓ 发起系统调用，经过受控入口
进入内核态
   ↓ 检查请求与参数，执行系统服务
返回用户态
   ↓
继续用户代码
```

### 定时器：让操作系统能够重新取得 CPU

只有权限分级还不够。如果用户程序一直做合法计算、从不主动请求服务，也不主动结束，系统仍需要重新获得 CPU 的机会。

**定时器（Timer）** 可以在指定时间后产生中断。操作系统在交出 CPU 之前设置它，到期后由中断使系统重新获得控制，进而决定继续执行、切换任务或处理超时。

```text
操作系统设置定时器
        ↓
调度用户程序执行
        ↓ 到期产生中断
CPU 进入系统处理程序
        ↓
系统重新作出执行安排
```

教材的可变定时器模型由固定频率时钟和计数器构成：**操作系统设置计数值，时钟每次滴答使计数器递减，到零时产生中断。** 课件第 55 页将递减动作简写成操作系统执行；机制细节按教材这一描述区分。

<details>
<summary>教材例子与习题 1.9：怎样利用定时器估计经过的时间？</summary>

教材举例：设周期性定时器每秒产生 250 次中断，那么每次间隔为

$$
\Delta t=\frac{1}{250}\ \text{s}=4\ \text{ms}.
$$

从某个已知起点开始，若累计了 $k$ 个这样的时钟间隔，则经过时间可估为

$$
t\approx k\Delta t.
$$

这是对教材固定周期模型的推导。它的精度受时钟分辨率及实际计时机制影响；“250”是示例配置，不能据此认定所有 Linux 系统的定时器均采用这一频率。

设置定时器的操作需要保护，否则用户可以让系统失去预期的抢回控制机会。

*教材 §1.4.3，pp. 26–27；习题 1.9，p. 53。*

</details>

## 操作系统的主要管理职责

> 本节对应后续课件第 56–64 页；AI 对照页集中到后文。这里掌握“管理什么、为什么需要、负责哪些活动”，具体算法留到相应章节。

### 进程管理

**进程（Process）** 是执行中的程序，是系统中的工作单位。**程序是被动的代码与数据，进程包含正在推进的执行活动和状态。**

同一程序可以对应多个执行实例。进程需要 CPU 时间、内存、I/O、文件以及初始化数据；终止时，系统需要回收其中可重复使用的资源。

| 情形 | 执行状态 |
| --- | --- |
| 单线程进程 | 有一条执行序列，以一个程序计数器记录下一条指令位置 |
| 多线程进程 | 含多条执行序列，每个线程有自己的程序计数器 |
| 多个进程 | 可以共享 CPU 时间，也可以在多个处理核心上并行推进 |

例如，浏览器进程接收 URL 作为输入，需要内存保存数据、CPU 执行处理逻辑，还需要通过系统提供的网络与显示能力完成访问和呈现。

操作系统的进程管理职责包括：**创建与删除、调度、挂起与恢复、同步、通信，以及提供死锁处理机制**。这些活动既涉及用户进程，也涉及系统进程。

**同步**协调并发活动的执行关系；**通信**让进程交换信息；**死锁处理**面对的是有关活动互相等待、无法继续推进的问题。本章只建立这些任务的全局位置。

*来源：课件第 56–57 页；教材 §1.5.1，pp. 27–28。*

### 内存管理

主存保存正在执行的指令和数据，是 CPU 与 I/O 工作的重要交汇点。内存管理需要决定：**何时把哪些内容放入主存，给谁多少空间，哪些内容可以移出。**

| 管理活动 | 具体问题 |
| --- | --- |
| 记录占用情况 | 哪些区域正在使用，由哪个进程使用 |
| 分配与回收 | 新需求使用哪些空间，释放后哪些区域重新可用 |
| 决定移入与移出 | 哪些进程、进程部分或数据需要驻留，哪些可以暂时移走 |

这些决策影响 CPU 利用率和用户响应。不能只看总容量，还要看多个进程如何共享、谁拥有哪些区域，以及访问是否被正确保护。

*来源：课件第 59 页；教材 §1.5.2，pp. 28–29。*

### 文件系统管理

**文件（File）** 是操作系统提供的逻辑存储单位。不同介质的访问速度、容量、传输速率、顺序／随机访问方式可能不同，文件系统向上提供相对统一的组织与访问方式。

文件通常由目录组织，系统还要决定哪些用户或进程可以访问哪些文件。

| 文件系统职责 | 作用 |
| --- | --- |
| 创建与删除文件、目录 | 管理逻辑对象的存在与组织 |
| 提供文件与目录操作 | 让程序能够读写、查找和组织信息 |
| 将文件映射到辅助存储 | 把逻辑内容落实到具体存储位置 |
| 访问控制 | 限制谁能进行何种操作 |
| 备份 | 将内容保存到适当的非易失性介质 |

这与本章开头“保存图片不需要指定磁道”相呼应：**用户使用逻辑对象，系统维护逻辑对象与物理存储之间的关系。**

*来源：课件第 61 页；教材 §1.5.3，p. 29。*

### 大容量存储管理

磁盘等设备保存主存容纳不下的数据，以及需要长期保留的内容。存储系统的管理会显著影响包含大量 I/O 的工作负载。

课件列出三个核心任务：**空闲空间管理、存储分配、磁盘调度**。分别回答哪里还能存、把数据放到哪里、接下来处理哪个访问请求。

**三级存储（Tertiary Storage）** 可用于不要求快速在线访问的数据，例如光盘、磁带上的备份和归档。它仍需要管理，但目标和性能要求与主存、常用磁盘不同。

介质还可以按可写性区分：**一次写入、多次读取（WORM）**与**可反复读写（RW）**。

### I/O 子系统：缓冲、缓存与假脱机

I/O 子系统的一个目标是**隐藏不同设备的具体差异**，让应用无需针对每一种设备重新处理所有硬件细节。它提供通用设备驱动接口，并依靠具体驱动适配相应设备。

| 机制 | 主要作用 | 与其他机制的区别 |
| --- | --- | --- |
| **缓冲（Buffering）** | 在传输过程中暂存数据，协调不同阶段的处理 | 关注数据正在传送或等待交接 |
| **缓存** | 将数据副本放到较快的存储，以便后续访问 | 关注重复使用与降低访问代价 |
| **假脱机（Spooling）** | 先收集、保存设备工作，再排队交给设备处理 | 使多个作业不必直接争抢只能逐项处理的设备 |

同一块内存可以兼有缓冲与缓存作用。例如，暂存磁盘数据以组织传输，同时保留其中内容供后续读取使用。

<details>
<summary>教材例子：多个人同时打印，为什么需要假脱机？</summary>

打印机需要有序完成输出，不能把多个文档的数据流任意交错打印。

系统先把各应用的输出保存在各自的假脱机文件中，排入打印队列，再依次交给打印机。应用提交输出与打印机实际打印在时间上被分开，多个应用可以先提交任务，不必都占着打印机等待。

用户还能查看队列、取消未打印任务或暂停打印。具体由系统服务还是内核线程实现，属于后续章节内容。

*教材 §12.4.3–12.4.4，p. 511；课件第 63 页只给出机制概览。*

</details>

*来源：课件第 62–63 页；教材 §1.5.4–1.5.6，pp. 30–32；缓冲／缓存／假脱机的展开见 §12.4，pp. 510–511。*

## 保护与安全

### 两类问题

| 概念 | 核心关注 | 本章例子 |
| --- | --- | --- |
| **保护（Protection）** | 控制进程或用户对系统资源的访问 | 限制内存、文件、CPU 和设备的使用权限 |
| **安全（Security）** | 防御来自系统内部和外部的攻击 | 拒绝服务、蠕虫、病毒、身份盗用、服务盗用 |

保护机制既要能**表达访问规则**，也要能**落实规则**。前面的双模式、受保护的设备操作、内存访问限制和定时器，分别帮助保护不同方面的系统运行。

安全的范围更广：即使提供了访问控制，还需要考虑身份被盗、程序被诱导、资源被恶意耗尽等情况。

### 用户身份、组与有效权限

系统通常先区分用户，再决定谁能做什么。

| 标识或机制 | 作用 |
| --- | --- |
| 用户标识 UID／安全标识 | 将用户身份与相关进程、文件联系起来，用于访问控制 |
| 组标识 GID | 把一组用户作为管理单位，统一配置某些访问权限 |
| 有效身份与权限提升 | 在受控条件下使用不同的有效身份，获得相应操作权限 |

权限提升需要服从系统规定的授权规则；“能够切换有效身份”不等于任何普通程序都能随意获得更高权限。

*来源：后续课件第 64 页；教材 §1.6，pp. 33–34。AI 代理的权限问题见后文。*

## 计算环境

### 从独立计算机到联网服务

课件展示了大型机、小型机、个人计算机、桌面互联网和移动互联网等形态的变化。办公室和家庭中的计算机逐渐通过网络共享文件、计算能力与服务，远程访问也使“本机资源”与“远端资源”的使用边界更加灵活。

本章更重要的问题是：**任务在哪里执行，资源由谁提供，访问与权限由谁管理？** 课件中的旧桌面截图和具体产品名称用于展示演变，不作为当下市场或硬件配置的统计。

### 客户端—服务器与对等系统

**客户端—服务器（Client–Server，C/S）** 模型中，客户端提出请求，服务器提供服务。

| 服务器类型 | 提供的服务 | 例子 |
| --- | --- | --- |
| 计算服务器 | 执行请求的动作并返回结果 | 数据库接收查询、计算并返回数据 |
| 文件服务器 | 通过文件接口提供存储与访问 | 客户端创建、读取、更新或删除文件 |

**对等系统（Peer-to-Peer，P2P）** 中，参与节点具有对等地位，一个节点可以请求服务，也可以向其他节点提供服务，不固定为单一角色。

| 比较项 | 客户端—服务器 | 对等系统 |
| --- | --- | --- |
| 角色组织 | 区分请求方与提供方 | 节点可同时承担两种角色 |
| 服务提供者 | 服务集中在指定服务器一侧 | 多个对等节点可以提供服务 |
| 如何找到服务 | 客户端寻找相应服务器 | 可通过中心目录登记，也可通过发现协议寻找 |

**P2P 不必意味着完全没有中心组件。** 课件列出两种发现方式：加入网络时向中心查询服务登记；或者通过发现协议广播请求，由能提供服务的节点响应。教材以 Napster 的中心索引、Gnutella 的分布式发现作历史例子。

*来源：后续课件第 66–69 页；教材 §1.10.1、§1.10.3–1.10.4，pp. 40–44。*

### Web 与云计算

Web 计算使用户能够通过网络使用远程内容和应用。课件提到**负载均衡器（Load Balancer）**：把访问请求分配给提供同类服务的服务器，协调服务器之间的工作负担。

**云计算（Cloud Computing）** 通过网络把计算、存储或应用作为服务交付。课堂强调：每个节点仍有自己的操作系统，云平台在多个节点之上进一步组织资源。

```text
用户／应用提出服务需求
          ↓
云平台组织计算、存储与网络资源
          ↓
多个计算节点，各自运行操作系统
          ↓
各节点的 CPU、内存、存储与网络设备
```

#### 课堂例子：电商高峰期间怎样增加计算能力

课堂用平时与购物高峰的需求差异说明：平台可以根据负载增加参与处理的资源，再在需求下降后回收部分资源。

这个例子体现**把多个节点组织成可按需使用的资源池**。它并不保证任意单机程序在不作设计的情况下就能自动扩展；本章材料没有展开具体应用如何分布式执行。

### 专用与实时环境

课件目录列出专用系统，但没有为其安排完整的机制讲解。教材的嵌入式与实时系统部分可作为补充。

**嵌入式系统（Embedded System）** 面向特定设备或用途，可能只有简单交互，也可能运行较完整的操作系统。不同设计可以使用通用系统、专用系统软件或无操作系统的专用逻辑。

**实时系统（Real-Time System）** 的正确性还依赖时间约束：**既要结果正确，也要在规定期限内完成。**

<details>
<summary>教材例子与思考题 1.3：机械臂已经撞上工件，再给出正确的停止命令，有用吗？</summary>

教材用机械臂说明：即使“停止”这个结果在逻辑上正确，晚到也无法满足任务要求。系统必须在规定期限内作出反应。

因此，设计实时操作系统的核心困难之一，是在资源竞争、中断与任务调度等情况下仍满足给定的时间约束。评价不能只看平均速度，也不能用“通常很快”替代期限保证。

</details>

## AI 时代的操作系统问题

> 这一部分整理课件中的 AI 拓展，保留与本章机制的联系。第 21–23、28、35 页出现在本次课堂记录中；第 58、60、65、71 页属于后续课件。相关产品和研究名称按课件的概念示例理解，本节不据此判断其实际部署范围或最新能力。

### 从操作步骤到用户意图

传统界面要求用户指定命令或操作，例如打开浏览器、进入网站、搜索航班。课件中的 AI／代理界面让用户直接陈述目标，再由系统解释意图、分解任务、选择工具、观察结果并调整计划。

| 交互形态 | 用户主要表达什么 |
| --- | --- |
| 命令行 | 要执行的命令 |
| 图形界面 | 要点击的操作 |
| Web／触摸交互 | 要使用的服务与操作 |
| 大语言模型 | 用自然语言表达意图 |
| 智能体／代理（Agent） | 委托一个需要多步完成的任务目标 |

课件的例子是：**“为我规划下周的东京旅行，预算低于 2000 新元。”** 用户给出目标和约束，代理尝试组织查询与计划过程。

这引出系统问题：**从意图到动作的转换，应该放在普通应用、系统服务，还是新的运行时抽象中？**

### “AI 操作系统”的三种含义

| 层次 | AI 在哪里 | 课件描述的角色 |
| --- | --- | --- |
| AI 运行在操作系统上 | 普通应用层 | 使用文件、进程、网络和设备接口，如聊天应用 |
| AI 能力进入系统服务 | 系统提供公共 AI 能力 | 向应用提供模型、加速器服务和可调用工具 |
| 代理运行时／Agent OS | 在现有基础设施之上管理代理任务 | 管理调度、上下文、记忆、存储和访问控制；课件以 AIOS 相关研究为例 |

**AI 层不替代内核。** 进程、内存、文件、I/O 和保护机制仍需要底层系统实现。新增层主要把高层目标转换为具体系统动作。

### 新的资源管理压力

课件第 35 页把经典操作系统资源与 AI 运行时压力作了对照。

| 经典资源 | AI 场景需要进一步管理的对象 |
| --- | --- |
| CPU 时间 | GPU／NPU 等加速器时间 |
| 主存空间 | 模型权重的装入、驻留与卸载 |
| 存储与文件 | 模型和任务状态的保存与访问 |
| 运行状态 | 推理过程中的 KV 缓存和会话状态 |
| 计算与响应预算 | 上下文容量、延迟、生成 token 数和能量等约束 |

这张表表达的是新增管理压力，并非严格的一一对应关系。课件指出相关职责分布在**内核、驱动、运行时与框架**中；不能把模型上下文或推理预算的全部管理都归给内核。

课堂用 KV 缓存保存推理中可复用的中间结果，说明避免重复计算的价值。它与前面的缓存共享“保存可复用信息”的思路，但本章没有展开其具体结构或算法。

### 进程与代理任务

进程是程序执行的基本单位；代理任务则增加了目标、计划、工具和跨轮次记忆等高层信息。

| 观察对象 | 需要管理的状态 |
| --- | --- |
| 进程 | 身份、地址空间、线程与程序计数器、打开的文件和网络连接 |
| 代理任务 | 模型与指令、目标、当前计划与上下文、工具及外部服务、跨交互的记忆 |

一个代理任务可能跨越多个进程和服务，也可能创建子任务。因此，进程机制仍保留，新的问题包括：**怎样调度任务、怎样保存和恢复进度、怎样隔离任务，以及怎样统计资源消耗。**

### 内存管理与上下文管理：类比的边界

| 操作系统内存管理 | 代理上下文管理 |
| --- | --- |
| 哪些字节或页面当前驻留主存？ | 哪些信息当前应该进入上下文？ |
| 管理明确的地址与数据内容 | 管理任务相关的信息与语义 |
| 使用缓存、主存、文件等层次 | 使用活动上下文、KV 缓存、检索到的记忆／文件／数据库等 |

课堂提到长时间、多轮次的数据分析：代理可能逐渐忘记最初目标，或重复尝试已经失败的方法。这个例子说明，需要保存任务状态，并在后续推理中取回必要信息。

**语义上下文不等同于虚拟内存。** 两者在“容量有限、需要决定保留与取回什么”上具有类比，但管理对象、机制和正确性要求不同。课件第 60 页明确要求保留这一边界。

### 当软件能够主动行动，权限如何控制

课件的任务示例是：**“找到我的机票收据，并提交报销。”** 它涉及邮件、文件、浏览器及业务系统，权限范围远超单纯生成一段文字。

| 原则 | 对应系统要求 |
| --- | --- |
| 最小权限 | 仅提供完成当前任务所需的工具与数据访问能力 |
| 确认 | 对影响较大的动作要求明确批准 |
| 隔离 | 分离代理的凭据、会话与运行环境 |
| 审计与来源记录 | 记录哪些数据、提示和工具调用导致了某个动作 |

课件还提出**提示注入（Prompt Injection）**风险：不可信内容可能影响一个已经拥有真实操作权限的组件。因此，关键问题包括“模型可以提出哪些动作”与“系统允许哪些动作真正发生”。

<details>
<summary>按课件例子分析：读取收据与提交报销需要同一份权限吗？</summary>

“找到收据”需要读取相关信息；“提交报销”还会改变外部业务系统的状态。这两步对权限与用户控制的要求不同。

按课件的最小权限与确认原则，可将任务拆开：先在授权范围内查找并整理材料；在执行提交等重要动作前，检查权限并取得相应确认；同时记录使用了哪些资料和执行了哪些操作。

这是对课件原则的应用，不代表本章已经给出完整的代理安全实现。

</details>

### 必须保留的系统边界

课件最后区分两侧的职责：

**操作系统机制**提供进程、线程、地址空间、系统调用、隔离和资源统计，目标是正确、可预测、可审计。

**模型与代理**负责意图理解、计划分解、工具选择、调整和语义记忆，其行为具有生成性并依赖上下文。

**本章留下的设计问题是：哪些选择可以交给 AI，哪些约束必须由操作系统和受信任组件强制执行？**

## 教材补充

> 以下内容用于补齐教材第一章的概念框架。课件目录提到体系结构，但没有像教材一样逐项展开；这些条目不等同于本次课堂额外讲授内容。

<details>
<summary>计算机体系结构：单处理器、多处理器、多核与 NUMA</summary>

教材 §1.3 按通用处理器的组织方式分类。

| 组织方式 | 关键特征 | 操作系统需要考虑什么 |
| --- | --- | --- |
| 单处理器系统 | 教材的基本模型只有一个通用处理核心；仍可含磁盘、键盘等专用控制器 | 在有限 CPU 执行能力上安排程序与设备工作 |
| 多处理器系统 | 多个处理器共享部分资源，能够同时执行工作 | 调度、资源竞争、协调开销、缓存一致性 |
| 对称多处理（Symmetric Multiprocessing，SMP） | 对等处理器都可执行系统功能与用户任务 | 分配负载，避免一部分处理器忙碌、另一部分空闲 |
| 多核系统 | 多个计算核心位于同一个芯片上 | 有效使用多个执行核心，并考虑它们共享的资源 |
| 非一致内存访问 NUMA | 共享物理地址空间，但访问本地与远端内存的代价不同 | 协同安排 CPU 与内存，减少昂贵的远端访问 |

教材给出每核有独立寄存器和一级缓存、同芯片共享二级缓存的双核示意。它是一个具体设计例子，不能推断所有多核芯片的缓存共享方式都相同。

增加处理器通常能提高吞吐量，但资源竞争和协调也会增加开销，因此不能仅凭有 $N$ 个处理器，就断言一个任务一定加速 $N$ 倍。

NUMA 的要点是**共享地址空间不意味着每次内存访问代价相同**。某个 CPU 访问自己的本地内存较快，访问其他节点的内存需要经过互连，可能更慢。

*教材 §1.3.1–1.3.2，pp. 15–19；图 1.8–1.10。*

</details>

<details>
<summary>集群与分布式系统：多台计算机怎样共同提供服务</summary>

**集群系统（Clustered System）** 将多个独立计算机节点连接起来，每个节点本身也可能是多核系统。它与“同一台机器内部有多个核心”需要区分。

教材强调集群的高可用目标：通过冗余、监测和故障后的接管，尽量在部分节点失效时继续提供服务。共享存储上的并发访问还可能需要锁与访问协调。

**分布式系统（Distributed System）** 由物理上分离、可能异构的计算机通过网络组成，使用户能够访问分散的资源。其收益包括资源共享、更多计算能力以及提高数据可用性的机会。

教材还区分：网络操作系统使各机器保持相对自主，并提供网络共享和通信；分布式操作系统进一步隐藏机器之间的差别，尝试提供更统一的系统视图。

这里的“统一视图”是一种对外抽象。底层通信、故障和资源分布的问题依然存在。

*教材 §1.3.3，pp. 19–21；§1.8，pp. 35–36。*

</details>

<details>
<summary>虚拟化：一台物理机上的多个执行环境</summary>

**虚拟化（Virtualization）** 把一台计算机的硬件资源抽象成多个执行环境。每个虚拟机可以运行自己的客户操作系统与应用。

**虚拟机管理器（Virtual Machine Manager，VMM）** 负责运行客户系统、分配资源，并保护不同客户之间的边界。教材同时介绍运行在宿主系统之上的实现，以及直接管理硬件的实现。

它可用于尝试不同操作系统、进行跨系统开发测试，或组织数据中心中的执行环境。

教材还将它与模拟作区分：在不同指令集之间执行原有机器代码，可能需要把源机器的操作转换为目标机器能够完成的操作，因而带来额外代价。不能只看到“运行另一个系统”就忽略底层体系结构是否兼容。

*教材 §1.7，pp. 34–35。*

</details>

<details>
<summary>内核数据结构：资源管理也需要具体的记录方式</summary>

教材 §1.9 总览链表、栈、队列、树、哈希映射和位图等结构。本章前面的设备状态表和请求队列，已经展示了“机制必须依靠数据结构记录状态”的思想。

| 数据结构 | 本章层次的理解 |
| --- | --- |
| 链表 | 用链接组织对象，支持按需要连接和移除节点 |
| 栈、队列 | 按特定顺序组织待处理对象 |
| 树 | 组织具有层次或次序关系的数据；平衡结构可避免过度退化 |
| 哈希映射 | 由键定位关联数据，需要处理哈希冲突 |
| 位图 | 每个资源用一个比特记录某种状态，适合紧凑地表示大量资源的可用性 |

**教材位图例子**：令 0 表示可用、1 表示不可用，位从左到右编号 0–8。

```text
编号：0 1 2 3 4 5 6 7 8
位图：0 0 1 0 1 1 1 0 1
```
